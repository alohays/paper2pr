# Review the presentation

Read the requested change, the presenter brief and the resolved deck profile. Keep established audience, chapter, demonstration and time decisions throughout. Review the build from the current verification run.

- **Copy edit.** Run `./verify <deck> --slide <id>`. Read the changed frame in context and check its final fragment and return path. Summarize the result in the handoff.
- **Numerical or factual change.** Check the exact claim, units, population, date and comparison against its declared primary source. Record the source and what it establishes. Inspect the affected frame.
- **New talk or release.** Run `./verify <deck>`, including classroom delivery when applicable. Obtain three independent reviewers. Give each the brief, relevant primary sources and frames from the same build. A factual reviewer checks consequential claims, numbers, attribution and demo labels. A visual reviewer checks legibility, final fragments, reverse navigation, captions, diagrams and media at the delivery sizes. A teaching reviewer works from the stated audience and assesses the agreed chapters, demo purpose, sequence and clock. Each reaches findings independently before synthesis. Report unavailable source evidence or a pending review explicitly.

For a review-only request, return grounded findings with slide IDs. When the request includes implementation, apply the supported fixes in scope and verify the changed build. One synthesis records the corrections, evidence and open questions for a release. Routine edits need a short handoff. Treat punctuation, line-length estimates, stylistic preferences and alternative examples as suggestions. A measured clip boundary or a conflicting primary source merits a specific fix.
